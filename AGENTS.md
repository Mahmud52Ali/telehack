# Инструкции для агентов

Общайся с пользователем и пиши пояснения на русском. Выполняй текущий запрос в пределах его задачи; наличие полного задания не означает поручение сразу реализовать весь проект.

## Контекст и источники

Проект для Всероссийского хакатона связи 2026: модуль сбора данных о СКЗИ по кейсу ФГУП «Главный радиочастотный центр». Приложение должно собирать сведения о личных сертификатах и версии Крипто Про на указанных ПК локальной сети, разбирать сертификаты и сохранять данные в БД.

- [Conditions/TASK.md](Conditions/TASK.md) — основное текстовое описание условий. Прочитай его перед первой задачей по реализации; дальше обращайся к нужным разделам.
- [Исходный PDF](Conditions/Original/Кейс%20№03%20ГРЧЦ%20(старт).pdf) — первоисточник для сверки спорных формулировок. Не рендери и не распознавай его заново без необходимости.
- `AGENTS.md` — правила работы в репозитории. Не подменяй ими требования кейса и не представляй собственные решения как условия организаторов.

Реализованы: `Telecom.sln`, библиотека `src/Telecom.Core`, WinForms-приложение `src/Telecom.App` и исполняемые проверки `tests/Telecom.Tests`. Есть парсер открытых сертификатов и файлов Windows-хранилища, сканер выбранной папки, XML-конфигурация, раскрытие масок папок, сканирование списка ПК через SMB, чтение ProductVersion КриптоПро и файловый журнал.

Режимы интерфейса — «Компьютеры» и «Папка». В списке ПК для подключения принимается только IPv4; отдельное необязательное название служит подписью. Повторяющиеся IPv4 запрещены. Выбранные ПК автоматически подключаются после открытия окна и повторно перед сканированием; сбой подключения одного ПК не останавливает остальные. Для подключения используются логин и пароль профиля. Список сохраняется в `%LOCALAPPDATA%\Telecom\computers.xml`, пароли — в диспетчере учётных данных Windows (`Telecom/Computer/<идентификатор>`). Для ранее сохранённого ПК без логина нужно указать логин и пароль через «Изменить».

Формат списка версии 3 сохраняет дополнительные пути каждого ПК. Они сканируются вместе с общими путями из выбранного XML. При чтении версий 1 и 2 дополнительные пути пустые, идентификаторы учётных данных сохраняются. В версии 1 прежнее сетевое имя становится подписью и требует ввода IPv4 через «Изменить».

В режиме «Компьютеры» `CertificateRepository` сохраняет результаты каждого проверенного ПК в MSSQL по строке подключения из выбранного XML. Столбец «База данных» показывает исход записи. Режим «Папка» выводит результаты в окно. Удалённый реестр пока не реализован. Примеры организаторов находятся в `Test_sert`. Проверяй фактическое состояние перед работой.

## Чистота репозитория

- Оставляй только файлы, необходимые для продукта, его сборки, проверок и постоянной документации. Создавай новый файл, только если у него есть конкретное назначение в текущей задаче.
- Временные скрипты, рендеры PDF, скриншоты, результаты OCR, выгрузки и разовые отчёты размещай вне репозитория, в отдельном подкаталоге системной временной папки. В PowerShell её путь доступен через `$env:TEMP`.
- В текущем рабочем окружении пользователь потребовал хранить рабочие кэши и временные файлы на диске D:, вне репозитория. Используй пользовательские значения `TEMP`, `TMP`, `NUGET_PACKAGES`, `NUGET_HTTP_CACHE_PATH` и `DOTNET_CLI_HOME`. Если процесс унаследовал старые пути на C:, перед сборкой и проверками обнови его переменные из `[Environment]::GetEnvironmentVariable(имя, 'User')`. Не создавай новые рабочие выгрузки и кэши на C:.
- Не создавай в репозитории `tmp/`, `output/`, `assets/`, каталоги кэша и аналогичные папки для обслуживания работы агента. Ресурсы самого приложения добавляй только при реальной необходимости.
- Не создавай без запроса журналы работы агента, файлы с планами, итогами сессий, чек-листами и дублирующими инструкциями. План, промежуточные выводы и отчёт о выполнении пиши в чате.
- Не дублируй условия, исходный PDF и существующие документы. Если информация передаётся обычным текстом, используй Markdown без картинок и внешних вложений.
- Артефакты сборки и тестов, локальные настройки IDE, логи и кэши не добавляй в Git. Когда соответствующие инструменты появятся, добавляй точные правила в `.gitignore`. Игнорирование не заменяет удаление разовых файлов агента.
- Не создавай пустые каталоги, заготовки компонентов и конфигурацию инструментов «на будущее». Используй существующую структуру; расширяй её по мере реализации.
- Перед удалением проверяй полный путь и содержимое. Удаляй только созданные тобой временные файлы либо явно указанные пользователем объекты. Сохраняй исходные материалы и чужие изменения; избегай очистки по широким маскам.
- Не сохраняй реальные пароли, секреты и локальные строки подключения в отслеживаемых файлах. Для необходимых примеров используй значения-заглушки.

## Ограничения задания

Это краткие ориентиры; полный состав требований и полей БД находится в `Conditions/TASK.md`.

- Язык реализации — C#, целевая платформа — .NET Framework 4.5. Используй совместимые API и зависимости; не заменяй целевую платформу без явного указания пользователя.
- База данных — Microsoft SQL Server (MSSQL). Результат должен собираться в `.exe` для Windows 10.
- Требуются чтение директорий из конфигурационного файла, сканирование, разбор сертификатов, сбор данных с указанных ПК и панель управления. Конкретные формат конфигурации, технология интерфейса и способ удалённого сканирования условиями не определены.
- Отсутствующую таблицу нужно создавать. Существующий сертификат определяется по серийному номеру: обновляй его запись и время обновления без добавления дубля. При первом внесении время обновления равно времени внесения.
- Ошибки работы и исключения должны попадать в файл логов; каждая запись должна содержать дату и время с точностью до миллисекунд.
- Примеры Java в условиях показывают оформление кода и не меняют требование использовать C#.

## Порядок работы

1. Определи цель текущего запроса по сообщению пользователя и относящимся к нему условиям. Изучи только нужные файлы; для поиска используй `rg` и `rg --files`, если они доступны.
2. Проверь существующие изменения. Если каталог уже находится под Git, используй `git status` и нужный `git diff`; если Git не инициализирован, не выполняй `git init` без запроса.
3. Выбирай простое решение, достаточное для задачи и совместимое с условиями. Не добавляй зависимости, слои архитектуры и сервисы без конкретной необходимости. Существенные допущения обозначай явно; задавай вопрос, когда без ответа нельзя корректно продолжить.
4. Вноси точечные изменения, сохраняя работу пользователя. Не включай посторонний рефакторинг и массовое переформатирование.
5. Доводи порученную работу до проверяемого результата без повторных согласований обычных обратимых действий. Не выполняй коммиты, push и публикацию без соответствующего поручения.

## Стиль и реализация

- Используй осмысленные имена переменных, типов и методов. Следуй принятому в коде стилю; пока его нет, используй `PascalCase` для типов и методов, `camelCase` для параметров и локальных переменных.
- По условиям кейса используй табуляцию для вложенных блоков и пробелы между операторами и операндами, включая условия.
- Комментарий к функции должен объяснять её действие. Не комментируй каждую очевидную строку. Поясняй нетривиальные ограничения и причины решений.
- Учитывай целевую платформу при выборе синтаксиса, компилятора и библиотек. Проверяй совместимость по реальной конфигурации проекта.
- Передавай значения в SQL через параметры. Не включай содержимое сертификатов и пользовательский ввод в текст SQL путём конкатенации.
- Не скрывай ошибки пустыми `catch`. При обработке исключений сохраняй сведения, необходимые для диагностики, и соблюдай требование файлового логирования.
- Самое важное: Соблюдай удобочитаемость и простоту кода. Чтобы человек, который видит его в первый раз не раздумывал над ним несколько часов.

## Сборка и проверка

- Сборка из корня: `dotnet build Telecom.sln -c Release`. Запуск интерфейса в PowerShell: `& .\src\Telecom.App\bin\Release\net45\Telecom.App.exe`. Проверки: `& .\tests\Telecom.Tests\bin\Release\net45\Telecom.Tests.exe` (код `0` — успех). Это исполняемые проверки, а не проект для `dotnet test`.
- Проверки MSSQL выполняются, только если в переменной окружения `TELECOM_TEST_SQL` задана строка подключения к отдельной базе с именем, оканчивающимся на `Tests`; они удаляют и создают в ней таблицу `dbo.Certificates`. Они также создают и удаляют на том же сервере базу `TelecomCreateTests` и учётную запись `telecom_restricted_test`, поэтому нужен отдельный тестовый сервер и права его администратора. Без переменной выводится `SKIP`. Строку подключения с паролем в репозиторий не добавляй.
- Для сборки нужен .NET SDK; пакет `Microsoft.NETFramework.ReferenceAssemblies.net45` версии `1.0.3` восстанавливается из NuGet. Целевая платформа всех трёх проектов — `net45`. Для запуска нужны Windows и .NET Framework 4.5 или новее. Проверки используют публичные образцы `Test_sert`; временные файлы создаются вне репозитория. Удалённый SMB и работа на Windows 10 должны проверяться отдельно на стенде.
- `src/Telecom.App/scan.config.xml` — отслеживаемый пример без секретов, копируется рядом с `.exe`. Настройки относятся к удалённым дискам. Версия КриптоПро читается из `ProductVersion` настроенного `csptest.exe`; отсутствие файлов отличается от отказа доступа. TCP-таймаут относится только к подключению к порту 445. Новая авторизация SMB и автоподключение требуют отдельной проверки на ВМ; автоматические сетевые сценарии используют тестовый адаптер. Статус соединения с `IPC$` не подтверждает прав чтения всех папок. Не разрывай существующие SMB-сеансы автоматически при ошибке `1219` или закрытии приложения. Проверки учётных данных создают и удаляют только свои записи с вымышленными паролями; настоящие учётки пользователя не используются. Не выдавай эти тесты за успешную проверку сети или полного охвата всех Windows-хранилищ.
- После появления проекта используй его реальные `.sln`/`.csproj` и совместимые инструменты. Не считай наличие современного .NET SDK подтверждением готовности сборки для .NET Framework 4.5.
- Когда добавляешь сборку или тесты, укажи здесь воспроизводимые команды и необходимые зависимости. Не фиксируй личные абсолютные пути и пути к кэшу конкретного агента.
- Проверяй поведение, затронутое изменением. Для записи в БД существенны создание отсутствующей таблицы, первое внесение и повторное обновление без дублей; для чтения и сканирования — корректные данные и ошибки; для логирования — запись исключений и времени с миллисекундами.
- Используй существующие проверки; добавляй тесты там, где они проверяют значимое поведение. Для правок документации достаточно проверки содержания, ссылок и отсутствия посторонних файлов.
- Если нужное окружение, SQL Server или доступ к тестовому ПК недоступны, прямо укажи ограничение. Не выдавай чтение кода за успешную сборку или интеграционную проверку.
